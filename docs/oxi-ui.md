# 🪟 OxiUI: One THTML/TCSS Source → Terminal, Web, Desktop, Mobile

This document is the implementation plan for evolving **OxiTerm** into **OxiUI**: a rendering engine in which the existing terminal renderer becomes *one backend among several* (TUI, web canvas, native GPU window, mobile), all driven by the same THTML/TCSS documents, the same session/state machinery, and the same App Server protocol.

> **Handoff:** see [HANDOFF.md](HANDOFF.md) (2026-11-25).
>
> **Status:** Phases 0–2, 3a–3c, 4 and 6 done; Phase 5 stages 5.0–5.1 done; Phase 7, Phase 5 stages 5.2–5.7 and Phase 8 (OxiScript) planned.

---

## 1. Goals and Non-Goals

**Goals**
- **One language.** THTML/TCSS stays the only markup/style format. No separate "UIhtml/UIcss". Backend-specific styling goes through `@media (render: tui|gui)` and silent-ignore of unsupported properties.
- **Zero regression for TUI.** Every existing app renders byte-identically over SSH and WebSocket after each phase.
- **Keep the server and protocol.** `oxiterm-server` (sessions, dispatcher, state, animations, `/events`, `/sessions/{id}/patch`) is not rewritten.
- **Lightweight GUI target.** Native window via `winit` + `wgpu`/Vello, aiming for a < 15–25 MB RSS footprint.
- **Two execution modes, same app source** (see §3.2):
  - **Server-driven:** the server renders, and a thin client (web, phone, desktop) only paints the DisplayList it receives over WS. This is the current OxiTerm model extended to pixels, comparable to LiveView for native apps.
  - **Local core:** parser, layout, session loop and renderer are compiled into the app (desktop binary, Android, WASM) and work offline. This is the Flutter-like model.

**Non-Goals (for now)**
- Full W3C HTML/CSS compatibility or a JS engine.
- Competing with Flutter on mobile polish (IME, accessibility, gesture physics) before the desktop/web path is solid.
- Proportional text before phase 6 (see §4).

## 3. Target Architecture

```
THTML + TCSS ──► parser ──► DOM arena + cascade ──► Taffy layout (f32, unit-resolved)
                                                          │
                                                   DisplayList builder
                                                          │
                        ┌─────────────────────────────────┼──────────────────────────────┐
                        ▼                                 ▼                              ▼
                 CellSink (TUI)                    Wire encoder (web)              GpuSink (native)
           DisplayList → CellBuffer          DisplayList → compressed msg      winit + wgpu / Vello
           → DiffEngine → ANSI / WS diff     → oxiterm-web canvas painter      (desktop, later Android)
```

### 3.1 DisplayList (core abstraction)

A flat, paint-ordered list of primitives in `f32` logical units:

```rust
pub enum DisplayItem {
    Rect      { node: NodeId, rect: RectF, bg: Color },
    Border    { node: NodeId, rect: RectF, fg: Color, bg: Color, style: BorderStyle, chars: BorderChars, radius: f32 },
    TextRun   { node: NodeId, origin: PointF, text: String, fg: Color, bg: Color, mods: Modifiers },
    PushClip  { rect: RectF },
    PopClip,
    Image     { node: NodeId, rect: RectF, asset: AssetRef },   // phase 3+
    Legacy    { node: NodeId },                                   // phase 1: img/video/diagram painted by the old path
}
```

Requirements the cell code gets "for free" today and the DisplayList must carry explicitly:
- **Paint order and z-index**: built from `LayoutResult.paint_order`, including `Position::Fixed` offsets.
- **Clipping**: an explicit push/pop pair. Today `safe_set` only clamps to the buffer edge.
- **Border glyph sets**: `Border` carries `chars`, so the TUI sink reproduces `┌─┐` / `╔═╗` / rounded exactly. GUI sinks use `style`/`radius` instead.
- **Node ids on every item**: for GPU hit-testing and a11y.

### 3.2 Two execution modes

```
                    ┌──────────────────────── oxiterm-core (no tokio, no network) ────────────────────────┐
                    │ DOM + cascade + layout + DisplayList + EventLoop + StateManager + animations        │
                    │ ActionHandler trait  ·  FrameSink trait  ·  FontBundle                                │
                    └───────────────▲─────────────────────────────────────────────▲─────────────────────────┘
                                    │                                             │
      SERVER-DRIVEN MODE            │                       LOCAL MODE            │
      oxiterm-server                │                       oxiterm-gui / Android / WASM app
      ├─ SSH  → CellSink → ANSI     │                       ├─ GpuSink (winit + wgpu)
      ├─ WS   → CellSink → diff     │                       ├─ input from winit/touch → EventLoop
      └─ WS   → DisplayList msg ──► thin client paints      └─ ActionHandler:
         ActionHandler = HTTP to App Server (ureq)              ├─ in-process Rust callbacks (offline)
                                                                └─ HTTP to App Server (same protocol)
```

- **One core, two hosts.** `EventLoop` already runs on a std thread with `std::sync::mpsc`. The tokio and network coupling is at the edges: `ClientSession.web_frame_tx`, the SSH reactor, and the `ureq` POST in `dispatcher.rs`. Extracting the loop into `oxiterm-core` behind two traits makes both modes the same code:
  - `FrameSink` (already exists in `oxiterm-renderer`) receives frames: cells for TUI, DisplayList for GUI.
  - `ActionHandler` replaces the direct `ureq` call. In server-driven mode it is the HTTP App Server client. In local mode it is either in-process Rust (offline apps) or the same HTTP client.
- **App source is identical in both modes.** The same `.thtml`/`.tcss` and the same App Server contract (`/events`, state patches). An app can start server-driven and later ship as a local binary without changes to its markup.
- **Text and hit-testing are consistent in both modes (resolves the old D1).**
  - Both modes use the same layout code and the same **bundled font** (`FontBundle`, loaded by `cosmic-text`/`parley`), so a document lays out identically wherever it runs.
  - In server-driven mode the DisplayList carries **already shaped, positioned glyph runs**. The thin client never re-measures text. It draws glyphs at the coordinates it was given, and sends pointer events back in those coordinates. The server hit-tests on the layout it actually sent, so there is no font-metric drift between server and client.
  - In local mode layout, painting and hit-testing happen in one process, so drift is impossible by construction.
- **Thin client = local core minus the session.** A thin client is the GPU/canvas sink plus input forwarding. It reuses `GpuSink` and the web painter from the local build, so the two modes share their whole rendering stack.

## 4. Open Decisions (need the owner's call)

**D1 / D2: Server-side vs client-side layout, mobile model. Decided: both.**
The owner chose to support both execution modes. §3.2 describes how: a shared `oxiterm-core`, a bundled font, and positioned glyph runs in server-driven mode. Remaining sub-choices are left to implementation:
- Phases 1–3 stay **monospace** (coordinates `f32` in `ch`/`lh`). Proportional text arrives in phase 6 for both modes at once.
- Which font ships in `FontBundle` by default (one monospace + one proportional family, chosen for small size and wide Unicode coverage).
- Thin-client distribution: web first (no install), then the same thin client as a mode of the native/Android app.

**D3: GPU rasterizer.** Vello needs compute shaders (modern GPUs). A custom instanced-quad renderer (GL 3.3 / GLES 3 / Vulkan) covers old hardware such as GT 220 and the OxiDE retro targets. These may end up as two sinks.

## 5. Phased Plan

> **Execution order (decided 2026-11-22):** phases are numbered by topic, not by order. After Phase 4 the order is:
> 1. **Phase 5 stages 5.0–5.1:** instrumentation and CPU-side wins. These are not GUI work, so every mode benefits.
> 2. **Phase 6:** proportional text.
> 3. **Phase 7:** WASM local mode, OxiDE framebuffer sink, and Android as a thin WebView shell around the web client (thin-client or WASM-local).
> 4. **The rest of Phase 5 last (5.2–5.7):** the native window with GPU rendering, which then also gives Android a native renderer.
> 5. **Phase 8 (OxiScript)** starts after Phase 7; its Stage 8.0 research spike can overlap with Phase 5.2+. Its order relative to 5.2–5.7 is the owner's call.

> **Process rule (owner, 2026-11-24, all phases from now on):** after every finished stage, before its commit is admitted, a separate **BAD ACTOR** agent tries to break it: fuzzing, sandbox/path escapes, malformed protocol input, resource exhaustion, crashes, wrong output, differential checks between modes. Findings are fixed or logged, and each becomes a regression test.

### Phase 2: Units and float geometry — ✅ done

Implemented with these deviations from the original scope:
- Lengths are `f32` in cell units, not a `Length { value, unit }` type. `ch`/`lh` mean cells; `px`/`dp` convert through a provisional 8×16 px reference cell until phase 6.
- `RenderMode { Tui, Gui }` lives in `oxiterm-proto`; `LayoutEngine::with_mode` selects it.
- TUI snapping happens only in the layout engine (`snap`/`snap_size` and rect flattening); Taffy's own rounding is disabled in GUI mode.
- `@media (render: tui|gui)` is applied at parse time via `THTMLParser::parse_with_mode`; `parse` = TUI. `border-radius` is parsed into `ComputedStyle.border_radius` (cells; TUI ignores it); `box-shadow`, `font-family`, `font-size` are ignored silently.
- `LayoutResult.total_height` stays `u16`, because scrolling is still cell-based.
- During transitions, layout now reruns every animation tick because values change below one cell; empty diffs are still not sent.

Original scope:
- TCSS lengths become `Length { value: f32, unit: Ch | Lh | Px | Dp | Percent }`. A bare integer stays `ch` horizontally and `lh` vertically, so existing TCSS is unchanged.
- `Rect` becomes `f32` (or a parallel `RectF`). The TUI sink snaps to cells with one documented rounding rule.
- `HitTester` takes `f32` points. TUI passes `(col + 0.5, row + 0.5)`.
- `animation.rs` stops rounding to cells in the style. Rounding happens only in the TUI sink, which gives GUI sub-cell smoothness for free.
- Add the `@media (render: tui|gui)` parser and evaluation, plus silent-ignore for GUI-only properties (`border-radius`, `box-shadow`, `font-family`, `font-size`).
- **Done when:** golden snapshots are unchanged, and `@media` tests cover both render modes.

### Phase 4: Extract `oxiterm-core` (enables local mode) — ✅ done

**Goal.** Move the session logic (event loop, state, focus/scroll/drag, animations, `<for>` expansion) out of `oxiterm-server` into an `oxiterm-core` crate. The core must **run**, not just compile, in a desktop app, on Android and in `wasm32-unknown-unknown`. `oxiterm-server` becomes a thin host: SSH, WebSocket, HTTP App Server client, metrics.

#### What the code looks like today (surveyed before planning)

| Area | Finding | Consequence |
|---|---|---|
| `session.rs` (4365 lines; ~2225 production, ~2140 tests) | `EventLoop::run()` is one ~570-line blocking loop (`recv_timeout` on the event channel, then render) | Must be turned inside out into a step API |
| Clock | `Instant::now()` in session.rs (resize debouncer, `last_activity`, render), `animation.rs`, `ratelimit.rs`, `throttle.rs`, and the renderer's media `cache.rs` | `Instant::now()` panics on wasm32 at runtime; the core takes time from the host |
| Threads | `dispatcher.rs` spawns a thread per App Server call (ureq); renderer `cache.rs` spawns decode threads | No threads in the core; async work goes through host traits |
| `ClientSession` | Mixes pure session state with transport (`web_frame_tx` tokio sender, `raw_input_tx`/`ReactorMessage`, prometheus `metrics`, token, epoch, connection count) | Split into a pure half (core) and a transport half (server) |
| Direct transport writes in the loop | Nav error (0x34/0x35), throttle notice and `open_url` (0x33) write `web_frame_tx` directly | Route through the sink like display lists and the ARIA mirror |
| Event channel | `backpressure.rs` uses `tokio::sync::Notify` | The host owns the channel and pushes events into the core |
| Page loading | `loader.rs` + `pathsafe.rs` read the filesystem | A `PageSource` trait: filesystem on the server, embedded or virtual FS on wasm |
| Already pure | `state.rs`, `events.rs`, `expand.rs`, `placeholder.rs`, `pathsafe.rs` logic | Move as-is |
| Installed targets | `wasm32-unknown-unknown` and `aarch64-unknown-linux-gnu` are installed; `aarch64-linux-android` is **not** | The Android check needs `rustup target add aarch64-linux-android` (an rlib build needs no NDK linker) |

#### Target API (step-based, host-driven)

```rust
// In oxiterm-core. `now` is a monotonic time supplied by the host; the core never reads a clock.
impl Session {
    fn handle_event(&mut self, ev: InputEvent, now: Millis);   // input, resize, patches, navigation
    fn tick(&mut self, now: Millis);                            // animations, debounces; emits frames via sinks
    fn next_deadline(&self) -> Option<Millis>;                  // when tick() must run again (None = idle)
}
trait FrameSink    { /* cells, display list, a11y (exists) */ fn send_notice(&mut self, n: ClientNotice) -> Result<bool>; }
trait ActionHandler { fn dispatch(&self, payload: DispatchPayload); } // fire-and-forget; the patch comes back as an InputEvent
trait PageSource   { fn load(&self, rel_path: &str, mode: RenderMode) -> Result<THTMLDocument>; }
```

- **Server driver:** a thread that does `recv_timeout(next_deadline - now)` → `handle_event`/`tick`. That is today's loop, outside the core.
- **Wasm and native drivers:** call the same three methods from their own event loop (`requestAnimationFrame`, winit).
- **Side effect:** the debounced resize becomes a deadline instead of waiting for the 1 s idle receive timeout. This fixes the open ~1 s resize lag.

**5.1b done** (incremental layout, 2026-11-24): `LayoutEngine` keeps its Taffy tree between `compute` calls (`oxiterm-renderer/src/layout/engine.rs`).
- *Reconcile instead of dirty tracking.* The document's dirty list is not trusted (bound text, animated styles and most other mutations never reach it). Every call walks the whole document and compares each node's inputs to Taffy (mapped style incl. `bind-show` display, measure-context text, child list) with what the kept node holds, and touches only what differs. `bind-show` flips, text edits, resizes (root style) and `<for>` appends are plain updates, no rebuild.
- *Full rebuild (fail safe)* when: no tree yet, a node of the kept tree is no longer reachable from the root (removed or freed, so a reused arena id cannot alias), a node would be adopted by a new parent while Taffy still lists it under an old one (Taffy's `set_children` rewrites parent links unconditionally, which would break dirty propagation), a node is reached twice, or any Taffy error.
- *Empty-cache solve.* If anything changed (or the root's available space did), every leaf is `mark_dirty`'d first, so the solve starts from an empty cache, as in a rebuild; only the node allocations and the tree drop are saved. Reason: the equivalence fuzz found a kept-cache solve that differed from a rebuild (GUI, `examples/index`, after a viewport-height change, a flex-direction flip and an append). Styles, children, parent links and contexts were identical to a fresh tree and marking everything dirty gave the rebuild's result, so it was a stale cache; whether Taffy's size-matching cache heuristic or a dirty-propagation gap from an earlier frame is the cause was not isolated. Do not retry partial cache reuse without a fix for that.
- *Quiet frame.* Nothing changed and same available space: Taffy's cache is hit (the solve is a no-op returning the previous result); flatten and paint order still run because they read `position` and `z-index` straight from the document. Scroll offset is applied at draw time and is not a layout input.
- *Equivalence cross-check.* In debug builds (default, `set_cross_check`) every `compute` also lays a clone of the document out from scratch on a fresh engine and panics, naming the node, unless the rects (f32 bits), paint order and total height are identical. That makes every existing test (goldens, display-list equivalence, trace harness, event-loop, a11y) an equivalence test. Dedicated coverage: `oxiterm-server/tests/layout_incremental.rs` (all examples without `<video>`, TUI and GUI, 70 random frames each with up to 3 edits of text, width, height, padding, margin, border, flex direction and grow, wrap, position, z-index, `bind-show` flips, appends, detaches with arena id reuse, child reordering, `compact`, cols and rows changes, all without `mark_dirty`; seeds 0 and 12, `LI_SEED=n` for others, 31 seeds run clean; asserts incremental > full, quiet frames occurred and every compute was checked), a test through the real `render_frame` (`layout_is_incremental_and_cross_checked_across_real_frames`: bound text, `bind-show` flip, resize, 1 full build in 24 frames) and the trace harness.

**5.1c done** (redundant per-frame GUI work, 2026-11-24). Wire output is unchanged; only computation is skipped.
- *Overlay snapshot + `diff_grids`* (`oxiterm-core/src/event_loop.rs`, `CellSink::diff_grids_rows`). The eager full-buffer snapshot clone and full `diff_grids` are gone. Each overlay (focus ring, predictive echo, scroll indicator) saves the one row it is about to write (`save_row`, once per row) from the buffer exactly as the display list left it; afterwards only those rows are diffed. A frame where no overlay branch is entered clones nothing and appends nothing. Equivalence: no code writes `buffer.back` between `render_frame_mode` and the first overlay write, so a saved row equals the snapshot's row, and `diff_grids` is row-major with untouched rows contributing nothing, so rows sorted ascending give the same items in the same order. Debug builds also take the eager snapshot and `assert!` the two results equal on every GUI frame, so every existing test (traces, goldens, event-loop) is an equivalence test. In practice a page with any interactive node auto-focuses it (`rebuild_focusable_nodes`) and a page taller than the viewport always paints the scroll bar, so most real frames do enter an overlay branch; for them the cost fell from a full-buffer clone + diff to about 1 us per row. The bench frames carry no overlay (focus `None`, no scroll bar), which is the 0 us row below; the "one overlay row" line shows the painted case.
- *ARIA JSON* (`oxiterm_a11y::AriaCache`). `build_aria_json` reads only the nodes reachable from the root, per node: id, tag, `text`, `placeholder`, `name`, `alt`, `input_type`, `event_htmx.is_some()`, `position == Fixed`, the layout rect (presence and x/y/w/h) and the number of children the arena resolves (preorder, so the tree shape is unambiguous even with dangling ids); globally: focus and the two origins. `AriaCache` serialises exactly these into a reused byte key (walk mirrors `build_a11y_tree`, no JSON, no allocation after warm-up), compares it with the previous key and, if equal, returns the cached JSON. The comparison is exact bytes, not a hash, so a hit cannot be a collision. Debug builds rebuild on every hit and assert equality (guards a future `aria_node` that reads a new field; add it to `encode_key`). `send_a11y` is still called every frame, so the sink's own dedupe and its reset on reattach behave as before. Unit test `aria_cache_matches_fresh_build_for_every_input_class` mutates each input class once.
- *`0x21` / `update_document`: left as is.* `WsFrameSink::update_document` sends a bare `0x21` and clears `sent_coordinates` on every frame (not only on a document swap, despite the comment). The client treats a one-byte `0x21` as `clearMediaLayer()`, so on pages with media the layer is cleared and every coordinate message is re-sent each frame (the cleared map makes `sync_preamble` see `coords_changed`). Dropping it would change the bytes a client receives (and the trace baselines), so it is not a pure skip. If it is ever to go, the clear must be sent only on a real document swap, with the client's media layer and the trace baselines updated together. `sync_preamble`'s own bookkeeping is a few clones and a hash lookup on pages without media and was not touched.

#### What the code looks like today (surveyed before planning, 2026-11-24)
- **Cell size comes from the client.** The web client measures `"M"` in the browser's own monospace font (`WebTerminal::new`), derives `cols`/`rows` from canvas pixels and paints with `16px monospace`. There is no server-defined unit. Server-shaped positions would not match what the client paints.
- **Text is measured in three places, all in whole cells.**
  1. `wrap:word` text goes through the Taffy measure closure (`measure_wrap_text`).
  2. `wrap:none` text and buttons get `text_intrinsic_width` pinned in `map_style`.
  3. `build.rs::text_item` wraps again on its own when it emits glyphs.
- **`Glyph { x, y, ch, advance }` is already `f32`,** so positioned runs fit the shape of the list. `ch: char` cannot carry clusters (combining marks, ligatures).
- **Pointer input is cell-quantised** (`0x02 col,row`, hit-tested at the cell centre). Narrow proportional buttons next to each other would get wrong clicks, the same class of click-miss bug as the earlier rendering drift.
- **No TCSS property inherits before layout.** Colours inherit only at paint time (`precompute_inherited_colors`), and `font-family`/`font-size` are swallowed as `Unknown` (`tcss.rs`). Fonts must inherit, and layout needs them.

#### Rules for the whole phase
- **The default GUI font stays monospace.** Proportional text is opt-in through `font-family`. On the TUI path and the mono path no shaping runs at all. This keeps golden snapshots and traces byte-identical, and the 5.1 benchmark from regressing.
- **TUI ignores all font properties.** A terminal has one font.
- **Measuring and painting read one shaped result.** The Taffy measure, intrinsic widths and the display-list builder share one text-layout cache keyed by (text, face, size, weight, style, max width). Line breaks therefore cannot differ between measuring and painting.
- **Layout never depends on the client's fonts.** Glyphs missing from the bundle (CJK, emoji) are measured with the Unicode cell width scaled to the reference cell, a deterministic advance on every platform.
- **Inputs, caret and predictive echo stay monospace in Phase 6.** They are cell-coordinate `CellGrid` overlays. Proportional inputs are a later step.
- **Out of scope:** system-font fallback, RTL/bidi checking beyond what the shaping library gives for free, and `font-size` in TUI.

**6.3 done** (2026-11-24). GUI layout measures text by shaping when its font is not the root default. Nothing paints from it yet (6.4).
- **Fast path:** a text leaf or button whose `ResolvedFont` has the root default face, size and line height (mono, 16 px, 20 px; `ResolvedFont::uses_cell_metrics`) is measured exactly as before, in whole cells, with no shaping and no cache entry. Bold and italic alone stay on it: the mono face is fixed-advance and a client's synthetic bold or slant does not change advances (only Regular faces are bundled; bold and italic are still part of the cache key for when real faces arrive). Anything else (sans at any size, mono at another size or line height) goes through the shaper. TUI never shapes and skips `resolve_fonts` altogether. Without the `text-shaping` feature every lookup misses and the cell measure is used.
- **Core:** `oxiterm-core` now enables `text-shaping` on the renderer, so the server and the local/WASM core measure identically. Cost for the wasm build (probe cdylib calling `LayoutEngine::compute`, release, `opt-level=z`, LTO, no wasm-opt): 1.22 MB raw / 425 KB gzip without shaping, 2.81 MB / 1.14 MB with it; of the +1.59 MB raw, 0.82 MB are the two embedded faces and about 0.77 MB the shaping code. Lazy font fetching for WASM is a Phase 7 item.
- **Units:** shaped widths are px / 9.6 (`CELL_W_PX`), heights are lines x line height px / 20 (`CELL_H_PX`). Default mono is exactly one cell per char and per line.
- **Pipeline** (`text/layout.rs`): each `\n` paragraph is shaped once, with no width limit, by the shared cosmic-text shaper; glyph id 0 (`.notdef`) gets the advance `unicode_cell_width(ch) x 9.6 x size / 16` px per cluster (a CJK char is 2 cells, so layout never depends on a client's fonts); lines are then broken by our own greedy whitespace breaker on those advances. Not delegated to the library because it would break between CJK ideographs (the mono path treats a CJK run as one word) and would break against the `.notdef` advance before it could be substituted.
- **Long-word rule:** the same as the mono path (`word_wrapped_line_count`): words are never split, an over-long word overflows on a line of its own (what cosmic's `Wrap::Word` does too, not `WordOrGlyph`). MinContent is the widest word, MaxContent the widest paragraph (trailing spaces included, as the mono intrinsic width counts them), a definite width resolves to `max.min(avail.max(min))` like `measure_wrap_text`. Trailing spaces at a soft break hang off the line; unlike the mono path, runs of spaces are kept, not collapsed.
- **Float guard:** a width at or above the max-content width (compared in cells, against the very value measure returned for MaxContent, with 1e-3 cells slack) uses the unwrapped layout, and a word still fits when it overshoots the limit by at most 0.01 px, so the last word cannot wrap on px/cell rounding.
- **Cache:** `TextCache` per `LayoutEngine`, keyed by the exact bits of (normalised text, face, size, line height, bold, italic, max width or none); the unwrapped layout is the base the wrapped ones derive from. Values are `Arc<TextLayout>` holding glyph byte ranges into the text, not strings. Bounded, but never by dropping the live working set: only at the start of a `compute`, and only when it holds more than 512 layouts or 40,000 glyphs (about 2 MB), the entries not used in the previous frame are dropped (stale keys from changed or animated text). A big page therefore never reshapes every frame; it keeps one entry set as large as its own text. A layout someone holds survives an eviction. The biggest example pages in sans (`reference/tcss`, `reference/thtml`, `demos/showcase`) hold at most 50 layouts and 1,345 glyphs, and a steady frame costs about 55 us (cold 1.5 to 2 ms).
- **Lifecycle:** the cosmic-text `FontSystem` (parses both faces) is process-wide, built lazily on the first non-default text node behind `OnceLock` + `parking_lot::Mutex` (std only, no tokio; shaping is a pure function of its arguments, so sharing cannot change a result, and the lock is held only for a cache miss). The cache stays per engine: the debug cross-check builds a fresh engine every frame, and a shared cache would make it vacuous for shaping. Measured (release, RSS, one process per measurement): building the shaper and shaping once costs about 1.5 MB; 200 sessions of the sans fixture cost 125 KB each against 60 KB each for the same page with its font declarations removed (a mono twin), so a shaped page costs about 65 KB more per session (the per-session cache and side map; the first sans session is about 1 MB above the first mono one). A mono-only server never builds the shaper. First frame of the sans fixture: 1.1 ms with the shaper cold, about 0.9 ms with a cold cache.
- **Fallback faces:** both bundled faces live in one font system, so a character the requested face lacks can come from the other one (box drawing in sans is taken from the mono face, one cell wide). `PlacedGlyph::face` records the face a glyph id belongs to; a painter must draw each glyph in that face, not in the layout's.
- **For 6.4:** `LayoutEngine::shaped_text(NodeId) -> Option<&Arc<TextLayout>>` holds the layout of every shaped text leaf and button at its final content width (rect minus padding and border, through the same guard function as measure), filled after each solve; `wrap:none` nodes hold the unwrapped layout. The builder must paint from it and never shape again from the rect. A test asserts stored lines x line height / 20 equals the measured height.
- **Incremental layout:** `MeasureContext` carries `font: Option<ResolvedFont>` (only for nodes off the fast path), compared by the reconcile with the text; a change of a node's own or an inherited font re-measures it, a bold-only change on the fast path changes nothing (quiet frame). `wrap:none` text and buttons pin their shaped size in the style, so the style compare sees a font change. The debug cross-check also compares the shaped side map with the rebuild's. The fuzzer gets font mutations from its own generator (the layout-edit sequence, seed 12 included, is unchanged), including parent-only family and size changes, starts also from the sans fixture, and a dedicated test checks parent-only changes re-measure descendants and return bit-identical rects when reverted.

### Phase 8: OxiScript, a general-purpose typed language with OxiUI as its first host (planned)
Research basis: [research/oxiscript-language.md](research/oxiscript-language.md) (2026-11-24; claims tagged verified / search-only / estimate / opinion). This section records the owner's goals, the principles that follow from them, and the decisions still open. Nothing here is implemented.

**Owner's goals (2026-11-24)**
- **Feels like TypeScript, runs like a compiled language.** TS-like syntax, inference and editor support, but statically and soundly typed.
- **Two ways to run one program:** "write and run" live (compile in milliseconds inside the core, hot reload) and compiled for release, natively, down to microcontrollers.
- **Primary persona:** a JS/TS frontend or Node developer who builds a toy with their kid on an ESP32 must feel at home: one-command flash, live reload, browser simulator, VS Code.
- **No artificial limits.** OxiUI is only the first host. The language must stay general enough that someone could later build safety-critical software (the owner's test case: a rocket) on it.
- **Modern hardware without assembler knowledge:** SIMD/SWAR, multi-core and GPU are used automatically by default, with explicit control for those who want it.
- **No wall between the language and graphics/GPU:** data-parallel code is written as ordinary functions, not in a separate shader language glued on through an API.
- **Automatic, but never silent:** after every build the compiler says what it placed where and why, so nothing slows down by surprise.

**Principles (decided)**
1. **The core language has no domain concepts.** UI, real time, safety and GPU are profiles, libraries and host APIs.
2. **Sound static types.** No `any`, no unchecked casts, explicit numeric types (integers distinct from floats, overflow traps by default), one absence value (`T | null`), `Result` with `?` instead of exceptions, UTF-8 strings, discriminated unions with narrowing. Bidirectional local inference keeps it light to write.
3. **One language, compiler-checked profiles, never dialects** (the SPARK/Ravenscar principle). Profiles such as `realtime`, `safety` and `kernel` are restriction sets the compiler checks (no allocation, no recursion, bounded loops, no ambient authority, ...), with the same semantics as unrestricted code.
4. **Data parallelism is general, GPU is a backend.** Parallel and SIMD constructs have the semantics of sequential code. Layers: (0) automatic data-parallel combinators over arrays/images/grids; (1) explicit `Simd<T, N>` types; (2) opt-in schedules, tasks and isolates. `kernel` functions are ordinary functions under the `kernel` profile; backends in order: CPU SIMD + threads, then WGSL/WebGPU, then SPIR-V/MSL via naga. Device residency and CPU↔GPU transfers are visible in types (hidden transfers killed C++ AMP). Graphics (pixel/vertex shaders, a "paint with this kernel" display-list item) is a library on top.
5. **Placement report and performance assertions.** Every build writes a versioned, human-readable report: what went to GPU, multi-core, which SIMD width, scalar, transfers per call, allocations on hot paths, with a stable reason code whenever the fast path was not taken. The LSP shows it as inlay hints next to the code. `@expect(simd | gpu | no_alloc | no_transfer | ...)` turns a silent de-optimisation into a compile error; only language-defined facts are assertable, heuristics are reported but not assertable (so compiler upgrades do not break builds). The same assertions serve as certification evidence.
6. **Capabilities, not ambient authority.** A program sees only the host APIs it is given (no files, network or clock unless passed in), declared in a small own IDL that compiles to plain Wasm imports. The WASM Component Model can be an adapter later.
7. **Own typed SSA IR, Core WebAssembly as the first backend and distribution format.** No dependency on Wasm proposals that some target engine lacks (WasmGC, threads, exception handling: wasmi lacks them; AssemblyScript was hurt by this). Live mode runs the module in an embedded interpreter (wasmi in the core; on the device wasmi or WAMR, see open questions). Release: Wasmtime AOT on 64-bit hosts, wasm→C (w2c2, MIT) plus the target's C compiler for 32-bit boards, ESP32 and the likely safety route, the browser's own engine on the web.
8. **Hot reload by instance swap.** A reload builds a new instance and swaps atomically; module-local state resets, persistent state lives in host-managed, schema-versioned state (OxiUI's StateManager), following Dart's rules.
9. **Determinism and a written spec from day one:** no undefined behaviour, defined overflow and float behaviour across targets, reproducible compiler output. These are what make qualification (DO-178C, IEC 61508, ISO 26262, IEC 62443) possible later.
10. **Tooling is part of the language:** one query-based front end in Rust (also built for wasm32, because the compiler ships inside the core) shared by the compiler, LSP and formatter; LSP and formatter at launch; good error messages; a `package.json`-like manifest without promising that npm packages run. The device tooling (flash, live reload over USB then WiFi, browser simulator on the wasm32 core, host-side REPL) lives around the compiler, so a safety build can drop it without losing language features.
11. **Permissive licences only** for every component (the on-device runtime included). Moddable XS, the Toit VM and Jaculus are GPL/LGPL, so they are references, not dependencies.

**Decisions (owner, 2026-11-24 — decided now, deliberately, accepting that some may be regretted later)**
1. **Memory model:** reference counting with compiler elision (Perceus-style) plus a cycle collector (Nim ORC-style). GC-like convenience for closures in event handlers, mostly deterministic freeing; the `realtime`/`safety` profiles forbid allocation on hot paths. Stage 8.0 measures it (counter overhead, atomics across threads mitigated by per-isolate data, code size on ESP32) but does not reopen the choice.
2. **Grammar:** our own grammar, files `.oxs`, designed so that a TypeScript developer simply *reads* it without learning it (same keywords, braces, arrow functions, `import`/`export`, type annotations after `:`; differences only where soundness requires them, and then with familiar spellings). Real TypeScript is not parsed (no accepting syntax we then reject).
3. **On-device live engine:** wasmi (pure Rust like the core, fastest interpreter in the treVM measurements). Its larger flash footprint is accepted.
4. **GPU in v1:** no, and the `kernel` profile is not in the MVP either. But the language must be designed so that adding it later is easy, not hard: no feature in the MVP may make data-parallel kernels or device buffers awkward to add (the GPU backend comes in 8.3b).
5. **Tools in v1:** web flasher (WebSerial) yes; blocks editor later.
6. **First standards target:** IEC 62443 and the EU CRA (the business model); IEC 61508 as the first functional-safety standard, later.
7. **Ownership and method:** the OxiUI project owns the compiler, in this repository (`oxiscript-*` crates), with the same workflow as the rest (owner decides, agents implement, lead reviews). **After every finished stage a BAD ACTOR agent runs** whose only goal is to break it: escape the sandbox, exhaust resources, crash the compiler or runtime, make it miscompile, defeat the type system. Fuzzing (compiler front end, IR, Wasm output, runtime host API), differential testing (interpreter vs AOT) and adversarial programs are part of admitting a commit, not an afterthought; whatever the bad actor finds becomes a regression test.
8. **npm:** the idea, not compatibility: naming and semver conventions and a `package.json`-like manifest; npm packages are not promised to run.
9. **Hot reload state:** module-local state resets on reload; persistent state lives in the host's StateManager.
10. **No plan B bytecode:** WebAssembly is the only IR backend and distribution format.
11. **Laws (inspired by Bend 2's `LAWS.bend`, without its dependent types).** A `law` is a first-class declaration of a property the code must satisfy, written in ordinary OxiScript and readable by a TS developer:
    ```ts
    law sorted_stays_sorted(xs: i32[]) {
      isSorted(sort(xs))
    }
    ```
    One syntax, three levels of checking:
    1. **Tested (default, every build in dev):** the compiler generates many inputs from the parameter types and searches for a counterexample (QuickCheck/Hypothesis-style property testing, shrinking the failing case). Cheap and immediate; also the BAD ACTOR agent's fuel.
    2. **Proven automatically (`safety` profile):** an SMT solver (Z3, MIT, or cvc5, BSD) tries to prove the law without hand-written proofs, as SPARK, Dafny and Verus do.
    3. **Proofs written by AI or a human, only when the solver cannot:** lemmas and hints are added next to the law. In the `safety` profile an unproven law is a compile error (the Bend 2 mechanism, as the last resort rather than the norm).

    Lesson from Bend 2 kept in mind: laws only protect what is written down (an under-specified law let its demo agent change the game rules), so law review is part of code review. Full dependent types are rejected: they would break "a TS developer simply reads it" and slow compilation.
12. **AI-friendliness as a design goal:** an unambiguous grammar; error messages with stable reason codes and a suggested fix, readable by people and models; a stable specification with model-oriented docs (`llms.txt`); the placement report and `@expect`; laws as machine-checkable targets for agents; a deterministic compiler, so an agent can rely on its own experiments.

13. **Pointer width is a target parameter (owner question, 2026-11-25).** v1 targets wasm32: 32-bit addresses and lengths in the ABI (4 GiB of linear memory per module), while `i64`/`f64` arithmetic is native 64-bit. Release builds are still native 64-bit machine code on 64-bit hosts (Wasmtime AOT, or wasm→C then the native compiler); only the per-module heap is 32-bit addressed, which is also what ESP32-class 32-bit MCUs need. Programs that need more than 4 GiB get a later `memory64` target (part of Wasm 3.0): pointer width stays a codegen/ABI parameter, never a deep assumption, and the switch is an ABI version bump, not a language change.

Remaining unknowns are measured, not re-decided, in Stage 8.0: wasmi compile latency for small modules, fuel overhead and `no_std` flash size on ESP32, RC overhead with elision.

Today OxiUI has no 3D. The server-driven design exists in [iot-screens.md §4](iot-screens.md) (three tiers chosen per client capability: 1 pixels for the 3D region, 2 projected 2D polygons as ordinary `Path`/`Text` items, 3 mesh once + camera matrix per frame). `Path` already exists in the DisplayList (Phase 3b), so tier 2 has its foundation.

Stages when scheduled: **9.1** tier 2 (server-side projection to `Path`, `<model>` element, flat shading, picking) — no GPU needed, works in browser, OxiDE, ESP32 thin clients and (coarsely) terminals; **9.2** tier 3 (mesh + camera to capable thin clients); **9.3** GPU path in local mode and the native window (needs 5.2); **9.4** OxiScript 3D API and kernel shaders (needs 8.3b). Each stage ends with a BAD ACTOR pass (malicious meshes, polygon floods, NaN geometry).

#### GPU after OxiScript: one device, several users (2026-11-25)
Phase 5's GPU work is no longer only "a faster painter". Three consumers now need the same wgpu device: the DisplayList renderer (5.2+), OxiScript `kernel` functions on the GPU (8.3b) and 3D (9.3). Consequences:
- **Design rule now:** one shared GPU context in the local core (device, queue, buffer/texture residency) used by the renderer, the script runtime and 3D; script kernels can write into textures that the display list draws directly ("paint with this kernel"), with no CPU round trip.
- **Dependency:** 5.2 (headless GpuSink on wgpu) becomes the foundation of 8.3b and 9.3. When OxiScript reaches 8.3b, pull 5.2 (and the shared-context design) forward; 5.3–5.7 (window, input, AccessKit, Pi) can stay last.
- **wgpu also runs in the browser** (WebGPU/WebGL2), so GPU acceleration of local mode in the browser does not need the native window at all; it can arrive with 5.2 + 7.1.
- **OxiScript v1 needs no GPU** (CPU SIMD + multi-core first), so nothing here changes the current order.
- **AI acceleration falls out of the same design (owner, 2026-11-25):** inference is mostly data-parallel kernels (matrix multiply, convolution, attention) over tensors, i.e. exactly the `kernel` profile + device buffers + shared GPU context + SIMD layers. AI stays out of the language core: a tensor library written in OxiScript on those layers, plus an optional `host:ml@N` capability that delegates whole models to optimised backends (e.g. `tract`, `burn`/`candle` — MIT/Apache; on ESP32-S3 the vendor's int8 kernels; NPUs where present), with the placement report saying where each model/layer ran. Prior art to study for 8.3b: CubeCL (Rust kernels compiled to WGSL/SPIR-V/CUDA, the backend of Burn — the closest existing analogue of our kernel design).
