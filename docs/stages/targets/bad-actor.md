## F1 detail (the core question)

"Can a module get the host to run Wasm features it did not allow?" Yes, conditionally, and the guard is not where the stage notes put it:
* The set of features the engine can run is decided by wasmi's Cargo features, not by `Host::with_options`. wasmi's `Config::default()` turns on SIMD, RELAXED_SIMD and MEMORY64 whenever those Cargo features are compiled in, and `with_options` never calls `wasm_simd(false)`, `wasm_relaxed_simd(false)` or `wasm_memory64(false)` (the setters do not exist without the features).
* `oxiscript-rc` depends on `wasmi = "2.0.3"` with default features (`memory64`, `wat`). Any build that links both crates unifies the feature in: `cargo test --workspace`, the gate's `merge`/`nightly` "unified" step (`cargo test -p ... -p oxiscript-rc -p oxiscript-runtime`), or a future binary that links `oxiscript-rc` + `oxiscript-runtime`. `cargo tree -p oxiscript-cli -e features -i wasmi` (the shipped `oxi`) shows no `memory64`/`simd`, so today's per-package `oxi` is safe.
* With unification: a `device` module with a table64 (`(table i64 ...)` + `call_indirect` with an i64 index) loads and runs on a Device host (returns 7); the ABI pre-scan only inspects the MEMORY section. With `--features wasmi/simd`: SIMD and relaxed-SIMD functions load and run on a Device host. `check_target` returns `Ok` for all of these (its own `host_set` validator says "not allowed", then it defers to the engine, which now accepts).
* The merge gate therefore WILL show `f1_nothing_undeclared_reaches_the_engine` red in the unified step: that is this finding, not noise.

## What held up
* 21 hand-written probes (every wasmparser 0.228 proposal flag with a runnable encoding: simd, relaxed-simd, tail-call incl. `return_call_indirect`, extended-const, EH `try_table`, legacy EH, multi-memory, memory64, table64, shared memory, atomics/threads, ref types externref/funcref/multiple tables, typed funcref, GC struct, trunc_sat, wide-arithmetic, custom-page-sizes) x 6 manifests x 3 hosts: in the default build nothing outside policy passes the engine; per-probe layer attribution is printed by `matrix` (`--nocapture`).
* Manifest abuse (39 cases, each also with the manifest section moved to the front of the module): case, NUL, BOM, fullwidth/Cyrillic lookalikes, duplicates, order of lines, CRLF, lone CR, U+2028, trailing comment, > 4096 padding, two sections in all 4 orderings, non-UTF-8, empty, trailing bytes / concatenated module. All consistent, no panic, never "ok" when it must not be, placement independent.
* Every prefix of a valid web module (all hosts) and every single-bit flip of its manifest: no panic, no hang, no load of a truncated module, a Device host never loads a `target web`/`server` manifest.
* wasm-smith differential fuzz (60 000 modules x 3 hosts, random target and feature subsets, all proposals on): 0 panics, 0 policy violations against an independent wasmparser oracle; 11 907 of the 180 000 loads reached `load::check`.
* ABI crate: all 64 target x feature-subset combinations round trip or are refused; 200 000 token-soup manifests (27 749 accepted): accepted manifests always satisfy `features <= target`, sorted, unique and print/parse idempotent; target table consistent (`min_target`, `allows`, nesting).
* `reload` to a higher-target module on a Device host is refused `E0411` and the old instance survives; `Module::new` is reached only through `Instance::build` (instantiate, instantiate_in, reload).
* 3.9 MB module near the cap: three validator passes cost about 90 ms in release (no DoS lever).
* CLI: `--target` values are strict (case, spaces, empty, homoglyphs, repeated flag rejected, exit 2); oxi.toml `target` strict (non-string, wrong case, duplicate key, wrong table); `--target` overrides oxi.toml; `explain OXS-E0411` works; `run --target T` identical output for all T.
* Parity: 85 `.oxs` programs (syntax corpus valid + templates + site examples + agent_test), `oxi build --target device|web|server`: 74 build and are byte-identical apart from the manifest section across all 3 targets, 11 fail identically (libraries without `main`); 0 differences. (.oxir programs: only the existing `all_targets_emit_the_same_code` covers them.)

## F1 severity evidence and what is new

* Shipped artifacts today are NOT unified: `cargo tree -p oxiscript-cli`, `-p oxiscript-runtime`, `-p oxiscript-playground` (native and `--target wasm32-unknown-unknown --features run`) show wasmi features `auto-dispatch deterministic stable std validate` only. The playground is built per package (sites/build.mjs, wasm-pack), the release job ships only `target/release/oxiterm-cli` (does not link the runtime). CI `ci.yml` runs `cargo test --workspace`, so the runtime test-suite itself runs on a memory64-enabled engine there (and on the gate's merge/nightly "unified" step), which is where F1 is live.
* Not new in this stage: the table64 blind spot is the 8.R pre-scan (`reject_reexports` only looks at the MEMORY section) and the missing `wasm_memory64(false)`/`wasm_simd(false)` calls are older. New in this stage: `check_target` detects the violation with its own `host_set` validator and then returns `Ok` ("not my business, the engine rejects it as E0408"), i.e. it is fail-open and makes the stage's "host must refuse anything outside max_target" claim depend on Cargo features. Its comment ("code the host could not run anyway stays E0408 from the engine") is only true while the engine lacks the feature.
* Honesty inversion under unification (`--features wasmi/simd`): `ENGINE_FEATURES` still lacks `Simd128`, so an honest `target web` + `features simd128` module is refused `E0411`, while the same code with an undeclared (or `device`) manifest loads and runs. Declaring is punished, lying is rewarded.

## Recommendations

1. Make `check_target` fail-closed: when the bytes validate under `all` but not under `allowed` (declared + Device base) the module is refused (`E0411` if the host could run it, otherwise a policy `E0408`) instead of `Ok`. Verified by data: this alone closes table64/memory64/SIMD/relaxed-SIMD regardless of Cargo features (wasmi's `simd` feature also turns on `wasmparser/simd`, so the validator can then see SIMD).
2. Extend the pre-scan to the TABLE section (reject `table64`) and imports of tables/memories, like it does for memories.
3. `oxiscript-rc`: `wasmi = { version = "2.0.3", default-features = false, features = [...] }` so it stops enabling `memory64`/`wat` for everyone; add a runtime `Cargo.toml` note or a build-time `compile_error!`/test that the engine has no `simd`/`memory64`.
4. Host-construction self-probe (debug or first `Host::with_options`): instantiate tiny SIMD, relaxed-SIMD and table64 modules against the configured engine and assert they are refused; this turns "the policy is in Cargo.toml" into an executable check. Keep my `f1_device_host_runs_...` test as the regression test (it must be green in the unified step too).
5. F2: either drop `MultiMemory` from `Target::Server` and `ENGINE_FEATURES` until an ABI bump (and fix abi.md line 5 accordingly), or set `max_memories` from `max_target`.
6. F4: write abi.md 3.6 (feature sets per target, `max_target`, `E0411`, the engine-feature intersection) and restore the `abi.md 3.4` trap citation in `runtime.rs`.
7. F3: emit the target per project in `check --json` (or refuse mixed projects), and warn on unknown `oxi.toml` keys (pre-existing: all unknown keys are ignored, not specific to `target`).
