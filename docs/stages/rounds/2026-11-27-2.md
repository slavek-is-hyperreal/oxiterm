### R2-10 MEDIUM: secrets present while npm installs
The deploy step (`env: CLOUDFLARE_API_TOKEN, CLOUDFLARE_ACCOUNT_ID` set on the step) runs `npx -y wrangler@4.86.0 deploy ...` in a loop. Only the top-level version is pinned; there is no `package.json`/lockfile in the repo, so every transitive dependency of wrangler (esbuild, workerd, miniflare and so on, some with install scripts) is resolved fresh from the registry on each release, in a process that already holds a token able to deploy to the account. A compromised transitive release steals the token, and the owner approval does not prevent it (the approval gates the job, not what npm runs in it).
Repro: read the step; `r2_10` asserts the token step contains no `npx`/`npm`; `r2_11` asserts a committed `sites/deploy/package-lock.json` exists.
Fix: add `sites/deploy/package.json` (wrangler 4.86.0 as an exact dependency) + `package-lock.json`; in the deploy job a step WITHOUT secrets runs `npm ci --ignore-scripts --prefix sites/deploy` (if workerd/esbuild need their install scripts, allow them explicitly); the secret step then runs only `sites/deploy/node_modules/.bin/wrangler deploy --config ...`. Optionally `npm audit signatures`.

### R2-01 LOW: display name normalisation collides (R1-04 variant)
R1-04 made `files[]`, `diagnostics[].file`, `edits[].file` and `file_targets` consistent, but the shared form is `to_string_lossy().replace('\\', "/")`. On Linux `a\b.oxs` (a file with a literal backslash) and `a/b.oxs` both become `a/b.oxs`. `check --json .` on a directory containing both (each with `a == b`) gives `files: ["a/b.oxs","a/b.oxs"]` and ONE diagnostic: the `seen` key `(file, start, end, code)` drops the second one, and `sources` is keyed by the same string. Effect: a file's error is invisible and shown under the other file's name; after fixing the visible file the error "persists". `--fix` itself is safe (`probe_fix_with_colliding_names_touches_only_own_file`: each file gets only its own fix; it works per file in memory and filters edits by the same name). Fix: dedup and `sources` on the real path (`PathBuf`), keep the normalised name for display only; or escape `\` in a file name (`\x5c`) instead of mapping it to `/`.

### R2-02 LOW: `carry` is not range-checked
The carry is a remainder (`< 5555`). `10#<digits>` has no bound: `carry=9223372036854775808` wraps to a negative number and the script prints a nonsense tag message (`carry=-292`). It needs a malicious or mistyped tag message (tag creation is owner-only), hence low. Fix: after the digit check require `${#CARRY_RAW} -le 18` (keeps `10#` exact and still accepts the zero-padded forms R1-51 deliberately accepts, e.g. `carry=00100`) and `CARRY -lt STEP`, else exit 1.

### R2-03 LOW: `forEach` with a mutating callback (R1-30 neighbour, outside hash/equals)
`Map.forEach` (and `Set.forEach`) capture `n = entryKeys.length` once and walk the live arrays. Remove visited entries from the callback (compaction replaces the arrays and shifts the remaining ones left of the cursor), then insert fresh keys until the length is back at or above `n`: the loop skips original entries that are still live and visits the new ones. Repro in the test: 40 keys, at the 20th visit remove 0..24 and insert 100..129; originals visited = 20, a sound iteration visits 35. No trap (shrinking compaction alone does trap on the bounds check, `probe_map_foreach_shrinking_compaction_traps_or_is_sound`). Fix: capture `modCount` in `forEach` and trap (bounds) when it changes between callbacks, plus one line in std.md ("do not mutate the collection from a forEach callback"). Does not block: no memory unsafety, the collections are bounds-checked.

### R2-12 / R2-13 / R2-14
- R2-12: set `persist-credentials: false` on the deploy checkout (nothing needs git after it); same for build as hygiene.
- R2-13: add `concurrency: { group: sites-deploy, cancel-in-progress: false }` to the deploy job.

### Info (no test)
- Environment `Cloudflare` (read with GET only): the custom deployment-branch policies are exactly the two tag patterns `oxiscript-v*` and `v*` (type tag); one required reviewer (the owner); `prevent_self_review: false` (right for a one-person repo, but then the approval is only as strong as the owner's attention); `can_admins_bypass: true` (expected for the owner; keep in mind if collaborators are ever added). The repo default workflow token permission is read; workflows cannot approve PRs.
- The workflow file that runs is the one at the tagged commit: whoever can push a tag can change the workflow, so the reviewer's approval is the only gate, and the approval screen does not show the diff. Check `.github/` changes before approving a tag.
- `v*` also matches tags like `vfoo`; harmless (build and check must pass, approval needed), but `v[0-9]*` is tighter (the environment policy uses the same patterns, update both).
- "Check the live sites answer" proves that the host answers 200, not that the new version is live (a stale deployment passes). Compare a version marker if that matters.
- Wrangler reads `_headers`, `_redirects`, `.assetsignore` from the assets directory, so a compromised build can change served headers (drop the CSP). The artifact is the site, so this is within its trust; nothing from the artifact is executed.
- `workers_dev: true` also publishes `*.workers.dev` for each worker: a second origin for the same static content.

## What held

Workflow (`probe_*` in `bad_actor_round2_workflow.mjs`):
- No `pull_request`, `issue_comment` or `workflow_run` trigger; only tag pushes and `workflow_dispatch`.
- Secrets appear only in the deploy job, in one step's `env`, never at workflow or job level, never in `build`; `build` has no `environment`, so cargo build scripts, `sites/build.sh`, node and npm there cannot read them.
- `permissions: contents: read` only, no `write` anywhere.
- `workflow_dispatch` with `deploy: true` on a branch ref: the `if:` requires `refs/tags/`; the environment policy independently rejects branches.
- `${{ }}` in `run:` blocks expands only `steps.pick.outputs.sites`, which is one of two string literals produced by a `case`; the tag name is read through the `GITHUB_REF_NAME` environment variable, not interpolated; `inputs.deploy` is a boolean used in an `if:`.
- A malicious build output cannot run in the deploy job: the artifact is downloaded into `sites/dist` only, `--config` comes from the tag checkout (`sites/deploy/*.wrangler.jsonc`), `npx` resolves from the checkout, and the configs point `assets.directory` at `../dist/<site>`; no artifact path is executed or used as configuration (only the assets themselves, see info).
- `sites/deploy/*.wrangler.jsonc` contain no account id, token, secret or vars; only the public domains.
- Wrangler version pinned exactly.

Round-1 fixes:
- R1-03 (`probe_hostile_file_names_never_reach_the_terminal`, `probe_hostile_paths_in_run_and_errors`): six hostile names (ESC/OSC/BEL, U+009B, U+202E, U+00AD, ZWJ, U+2028) through `check`, `check --fix`, `check --fix-only semicolons`, `fmt`, `fmt --check`, `build`, plus file arguments, missing files, `run`, `explain`, `new`: no unsafe character on stdout or stderr (JSON output excluded: the path is data there). `note()` and `fatal()` sanitise, `syntax_errors()` sanitises name and message.
- R1-04 (`probe_check_json_hostile_names_are_consistent`): for the six hostile names `files[]` holds the raw name, every `diagnostics[].file` and `edits[].file` is an entry of `files[]`, each file has its OXS-E0005, and `file_display` is present exactly when sanitising changes the name and is itself clean. The only inconsistency left is R2-01.
- R1-01: the cap is in `reject_reexports`, which is the only path before `Module::new` (runtime.rs `instantiate`; playground, CLI and the OxiPerf wasmi child all go through `Host::instantiate`). Locals are summed per compressed entry with `saturating_add` before eager compilation. Params are bounded by `MAX_PARAMS` (32) per function and `MAX_FUNCTIONS`.
- R1-30 (`probe_map_every_operation_traps_on_reentrant_mutation`, `probe_set_every_operation_traps_on_reentrant_mutation`): the matrix `{has,get,getOr,set,remove}` / `{has,add,remove}` x `{hash, equals}` x `{insert, remove, clear}` traps in every cell (30 + 18 programs). `rehash` uses cached hashes (no user call), `keys/values/entries` call no user code. `forEach` is NOT covered (see R2-03); the shrinking-compaction shape traps or is sound.
- R1-50 / R1-51: `bash -n` and `node --test scripts/test/bad_actor_round1_version.mjs` pass (the implementer could not run them). `probe_command_substitution_in_tag_is_refused_not_run`, `probe_patch_component_overflow_is_not_a_downgrade`, `probe_two_carry_lines_first_wins_and_crlf_is_refused` pass. Open: R2-02 only.
- R1-40: `parse_u32_checksum` rejects `7.0`, `1e2`, negative, string, bool, null, missing and above `u32::MAX` (serde `as_u64` is `None` for any float); covered by the crate's unit test; not re-attacked further.

## Verdict
Tag 0.0.3 after fixing R2-10 (a workflow-only change of about 10 lines: lockfile + install step without secrets). The fix has to land before the tag, not after: the deploy job runs the workflow file at the tagged commit, so a fix merged to main later does not change what the 0.0.3 tag runs. Alternative if the owner wants to tag first: tag, then reject the deployment approval (the build and checks still run, nothing is deployed) and let the sites update with the next tag. Nothing in the OxiScript code blocks the release (R2-01, R2-02 and R2-03 are LOW and can be tracked). The first release tag is the first thing that runs `sites-deploy.yml` with the real token, which is why R2-10 sits on the release path.
